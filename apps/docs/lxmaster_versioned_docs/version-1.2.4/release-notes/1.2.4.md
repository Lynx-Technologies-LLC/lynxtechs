# v1.2.4

_Released 2026-09-19_

## What's new

- **`eni_gen` now emits DC reference clock and cyclic ARMW/BRD datagrams** — when `--enable-dc` is on and the bus needs distributed clocks, the generator marks a `<ReferenceClock>` among the DC-active slaves and adds the cyclic `ARMW 0x0910` (System Time) and `BRD 0x092C` (System Time Difference) datagrams that TwinCAT/EC-Engineer-style DC ENIs rely on. Previously `eni_gen` only programmed the per-slave SYNC0 InitCmds and cycle/shift times, which left SYNC0 unable to start cleanly and caused PREOP→SAFEOP hangs on DC-capable buses. The reader, model, and validator were updated to round-trip these fields and to reject a SYNC0 bus that's missing a reference clock or the cyclic ARMW/BRD pair. `--no-dc` output is unchanged.
- **Ubuntu 26.04 LTS ("Resolute Raccoon") support** — `lxmaster` is now built, smoke-tested, and published natively for `resolute`.
- **Debian 12 (bookworm) support** — previously only asserted via a glibc-compatibility argument, it's now actually built and smoke-tested per release, not just claimed. (Debian 13/trixie is not included — see "Known gaps" below.)
- **Per-codename apt packaging** — instead of one `.deb` built on Ubuntu 22.04 and published to a single flat `stable` suite, every supported codename (`jammy`, `noble`, `resolute`, `bookworm`) now gets its own natively-built package and its own apt suite, so the shipped package always depends on whatever runtime libraries actually exist on that distro.

## Bug fixes

- Fixed `sudo apt install lxmaster` failing on Ubuntu 26.04 with:
  ```
  lxmaster : Depends: libxml2 (>= 2.7.4) but it is not installable
  ```
  Root cause: upstream libxml2 bumped its SONAME in 2.14 (`libxml2.so.2` -> `libxml2.so.16`), and Ubuntu 26.04 ships the renamed `libxml2-16` runtime package with no `libxml2` package at all. The old pipeline built one `.deb` on Ubuntu 22.04 and shipped it everywhere, so it always hard-depended on the `libxml2` name regardless of target distro. Every codename is now built against its own libxml2, so this class of break can't recur silently — a CI smoke test now asserts the package's runtime dependency identity and installability for every target before anything is published.
- Fixed `publish` rejecting every codename's package after the first with:
  ```
  ERROR: '...deb' cannot be included as 'pool/main/l/lxmaster/lxmaster_<version>_<arch>.deb'.
  Already existing files can only be included again, if they are the same, but: ...
  ```
  Root cause: reprepro's pool storage keys a `.deb`'s path on Package+Version+Architecture only — it does not know about Codename/suite. Every codename's build shares the same tag version (e.g. `1.2.3`), so `jammy`'s and `noble`'s `arm64` builds — genuinely different bytes, different `Depends` — both mapped to the identical pool path. reprepro accepted whichever codename published first and rejected every other codename's arm64/amd64 packages as a checksum mismatch on an "already existing" file. Fixed by giving each codename's build a distinct packaging `Version` (`<version>+<codename>`, e.g. `1.2.3+jammy`) via a new `LXMASTER_PACKAGE_VERSION_SUFFIX` CMake option — a standard Debian versioning idiom (cf. `+deb12u1`) that only affects the dpkg `Version:` field, not `lxmaster --version`'s output.

## Changes

- `release.yml`'s `build` job now builds inside per-codename Docker containers (`ubuntu:22.04`, `ubuntu:24.04`, `ubuntu:26.04`, `debian:12`) rather than relying on whichever OS image GitHub happens to offer as a hosted runner, with an explicit pinned compiler version per target.
- Added an install smoke test (dependency-identity assertion + real `apt install` + `lxmaster --version`) to the release pipeline, run for every codename/arch combination before publishing. One failing target blocks the entire release — no partial or degraded publish.
- `apt/conf/distributions` now defines one suite per codename instead of a single flat `stable` suite.
- The documented install command (README and the apt landing page) now checks the client's own codename against the supported list before touching apt, failing with a clear, named error on unsupported systems instead of a confusing apt dependency error.

## Known gaps

- **Debian 13 (trixie) — current Debian stable — is not published.** The release build compiles the installed shell scripts with `shc` (a casual-inspection deterrent, not a security boundary), but `shc` was removed from Debian testing on 2024-07-03 over an unsatisfiable build-dependency ([Debian bug #1072469](https://bugs.debian.org/1072469)) and never migrated back before trixie's freeze, so it isn't in trixie's repos at all. This was caught by the per-codename build's own CI (both `trixie amd64` and `trixie arm64` failed at "Install build dependencies" with `E: Unable to locate package shc`) before anything was published — trixie is deliberately left out of the build matrix and the apt suite list until this is resolved, rather than shipping a target CI can't actually build. `bookworm` (Debian 12, oldstable) remains supported.

## Note on v1.2.0 through v1.2.3

None of `v1.2.0`, `v1.2.1`, `v1.2.2`, or `v1.2.3` was ever actually published — all four
were tagged, built, and found broken by the release pipeline's own checks before a
package reached apt or a GitHub Release went out under any of those tags. There is no
user-facing regression to roll back, and no existing install to migrate away from any
of them.

- `v1.2.0`: every one of its 10 build combinations failed on the install smoke test's
  `apt-get install -y "$DEB_PATH"` line, which apt misparses as its `<package>/<release>`
  pinning syntax when given a relative path with no `./` prefix (splitting at the first
  `/` and looking up a nonexistent package named `build`). Fixed in the next tag by using
  `"./$DEB_PATH"`.
- `v1.2.1`: fixed the above, but its `trixie amd64`/`trixie arm64` build combinations then
  failed at "Install build dependencies" — `shc` isn't available on Debian 13 at all (see
  "Known gaps" above). Fixed by dropping `trixie` from the build matrix and apt suite list
  entirely rather than shipping a target CI can't build.
- `v1.2.2`: all 8 remaining build combinations passed, but `publish` then failed at
  "Add .debs to the repo (reprepro, per codename)" with `packages database contains
  unused 'stable|main|amd64' database`. The live apt repo (carried over from before this
  release's per-codename migration) still had database/pool state for the old flat
  `stable` suite, which no longer has a stanza in `apt/conf/distributions` — reprepro
  refuses to touch a repo with state it can't account for. Fixed by running
  `reprepro --delete clearvanished` (which permanently retires state for any suite no
  longer defined in `conf/distributions`) unconditionally before every publish; plain
  `clearvanished` without `--delete` only drops the empty database entry and still
  refuses to run while the old `stable` suite's packages are physically present.
- `v1.2.3`: fixed the above, but `publish` then failed again once it got past `jammy`:
  every other codename's package was rejected as a pool checksum mismatch against
  `jammy`'s (see the "Bug fixes" entry above for the root cause). Fixed by giving each
  codename's build a distinct packaging `Version`.

`v1.2.4` is the same content with all four issues fixed.

## Upgrade notes

- **Existing installs using the old `stable` suite will stop receiving updates.** If `/etc/apt/sources.list.d/lxmaster.list` contains `... https://apt.lynxtechs.com stable main`, update it to use your own codename instead:
  ```bash
  echo "deb [signed-by=/usr/share/keyrings/lxmaster.gpg] https://apt.lynxtechs.com $(lsb_release -cs) main" \
    | sudo tee /etc/apt/sources.list.d/lxmaster.list
  sudo apt update && sudo apt install --only-upgrade lxmaster
  ```
- No interim (non-LTS) Ubuntu release is published (24.10/25.04/25.10 are all already end-of-life). Only Ubuntu LTS releases and Debian 12 (oldstable) are supported — Debian 13/trixie (current stable) is not yet published; see "Known gaps" above. On any other distro/codename, build from source (see the README's Quick start).
